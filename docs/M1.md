# M1: shared durable task core and optional Relay

M1 is a developer/test slice, not a Windows capture application or production service. It executes only the deterministic Fake Agent. Local is the default and needs no URL, service, credentials, VPS or task-transfer network. Both transports call `packages/core/src/core.ts`; neither the Relay nor Worker implements another state machine.

Executed commands and acceptance mapping: [M1 verification record](M1_VALIDATION.md).

## Install and automated acceptance

Use Node **22.16+**, pnpm **10.19.0** and a dedicated private runtime directory on a local filesystem. Install/build dependencies once while online:

```sh
corepack pnpm install --frozen-lockfile
npm run check
```

`check` runs ESLint, strict TypeScript checking, all contract/integration tests and the TypeScript build. Root tooling/dependencies are shared across the workspace. `dist/` contains ordinary JavaScript with rewritten relative imports; source CLI scripts use erasable TypeScript syntax. SQLite is Node's experimental built-in `node:sqlite`; warnings are expected. Sharp includes a native image decoder and platform-specific optional packages. CI installs and tests independently on Linux/Windows and Node 22/24.

Tests use temporary directories, generated PNG/JPEG/WEBP, loopback HTTP and Fake only. No real screenshots, live tokens, Codex authentication or paid API is used. Acceptance includes shared one/five-image fixtures, process restarts and abrupt exit, Local network/listener denial, mode storage binding, role/owner auth, concurrent HTTP and multi-process SQLite claims, partial uploads, image decoding/hash refusal, storage fault injection, result conflicts, unstarted lease recovery and started-execution uncertainty.

## Local CLI (direct application calls)

From the repository root, PowerShell:

```powershell
$testRoot = Join-Path $env:TEMP ('shot2agent-m1-' + [guid]::NewGuid())
npm run local -- submit $testRoot 5
npm run local -- list $testRoot
npm run local -- work $testRoot
npm run local -- list $testRoot
# Copy the task UUID from the first output:
npm run local -- get $testRoot <task-uuid>
```

Expected: first output is `queued`; a separate `work` process reports `worked: true`; history shows `succeeded`, ordered hashes, attempt/profile/adapter attribution, Markdown and a private `result.txt` reference. A second `work` reports `false` when the queue is empty. `demo` submits and processes once in one process. It processes the oldest compatible queued task, so use a fresh directory for a standalone demo.

On Linux/WSL the same commands accept an absolute directory, e.g. `npm run local -- demo /tmp/shot2agent-m1 5`. Compiled entry: `node dist/apps/cli/src/local.js demo <directory> 1` after `npm run build`.

The Local module does not import the HTTP client/server. A subprocess acceptance test denies `fetch`, socket connections, HTTP requests and server listening, supplies an unusable Relay URL, then submits/reads/executes across independent processes. This also proves Local ignores Relay configuration.

## Remote loopback CLI

The M1 server listens on **127.0.0.1 only**. This is a local HTTP integration harness. TLS, a public listener, provisioning and production deployment are M5. `RemoteClient` accepts HTTPS or loopback HTTP, refuses redirects, and bounds request duration. Remote mode never silently falls back to Local.

In a PowerShell session, create disposable test credentials in environment variables (never commit or print real credentials):

```powershell
$captureToken = [guid]::NewGuid().ToString('N') + [guid]::NewGuid().ToString('N')
$workerToken = [guid]::NewGuid().ToString('N') + [guid]::NewGuid().ToString('N')
$env:SHOT2AGENT_DEVICES = @(
  @{ownerId='test-owner'; deviceId='capture'; role='capture'; token=$captureToken},
  @{ownerId='test-owner'; deviceId='worker'; role='worker'; token=$workerToken}
) | ConvertTo-Json -Compress
$env:SHOT2AGENT_RELAY_ROOT = Join-Path $env:TEMP ('shot2agent-relay-' + [guid]::NewGuid())
$env:SHOT2AGENT_PORT = '3100'
$relay = Start-Process node -ArgumentList 'dist/services/relay/src/main.js' -PassThru -NoNewWindow
$env:SHOT2AGENT_RELAY_URL = 'http://127.0.0.1:3100'
$env:SHOT2AGENT_TOKEN = $captureToken
npm run remote -- submit 5
$env:SHOT2AGENT_TOKEN = $workerToken
npm run remote -- work
$env:SHOT2AGENT_TOKEN = $captureToken
npm run remote -- list
# Stop the disposable server when finished:
Stop-Process -Id $relay.Id
Remove-Item Env:SHOT2AGENT_TOKEN, Env:SHOT2AGENT_DEVICES
```

Prerequisite: `npm run build`, and wait for the `M1 test Relay` listening message before submission. Expected: authenticated upload yields `queued`, Worker yields `worked: true`, capture history yields `succeeded`. A missing/invalid token receives 401; capture credentials cannot claim (403). Restarting the server with the same root/registry retains history. This is optional exploratory use; automated tests exercise these flows with ephemeral ports and close all resources.

## Persistence and failure decisions

- Each runtime directory contains a versioned SQLite database (`user_version=1`, WAL, `synchronous=FULL`, busy timeout) and private files. `TaskStore` and `BlobStore` are replaceable interfaces. Tasks/attempts/results commit under `BEGIN IMMEDIATE`. Immutable inputs and origin identity are normalized before digesting; unknown command/path/sandbox fields are stripped.
- Task IDs are globally unique; idempotency keys are unique per owner. A replay must match ID, key, authenticated origin device and all normalized input metadata. Changed input/key/ID returns 409. Replays verify submitted bytes and do not create more files.
- Upload format: exactly one first `metadata` JSON field followed by ordered `image-0` ... `image-N` file parts. Declared and actual type/size/hash must match. Limits: 20 images, 20 MiB each, 60 MiB total, one metadata field <=64 KiB. Sharp fully decodes under a **16-million-pixel cap** and rejects animated/multipage input; this M1 resource guard supplements the provisional byte limits. Uploads are bounded buffers, not unbounded streaming into published storage.
- Files use generated UUID names, exclusive creation, fsync and (POSIX) directory fsync before SQLite acknowledgement. Failed transactions remove newly staged files. A crash between file creation and DB commit can leave an **unreferenced private orphan**; it cannot create a visible partial task or become a downloadable URL. Orphan GC, quotas/retention and backup/restore tooling remain M5.
- POSIX directories/files use 0700/0600; symlink files and storage roots are refused, and every file read rechecks size/hash. Windows mode bits do **not** establish ACL isolation. Use a dedicated directory under the logged-in user's private profile and restrict its ACL before real data. Native Windows ACL assurance and power-loss durability need M5 proof. SQLite and blobs must share a trusted operator-controlled local volume; do not use network shares or a hostile writable ancestor.
- The store binds permanently to `local` or `remote`; opening it in the other mode fails. Selecting a different mode/root does not enumerate, copy or upload old tasks. No migration/synchronization feature exists.
- A claim atomically creates a UUID attempt and random fencing token. The coordinator permits one active execution globally. Capability ID/version must match; Worker independently resolves its read-only Profile. Start persists the Profile fingerprint and adapter version **before** Agent launch.
- Lease defaults to 30 seconds. Heartbeats extend only the current active attempt; the execution deadline never extends. Recovery runs on queue/history/file/lease operations using coordinator time: an expired unstarted attempt returns to `queued` with retained evidence, while any expired started execution becomes terminal `execution_unknown`. Coordinator restart alone does not invalidate an unexpired lease.
- `execution_unknown` covers Agent interruption, lease expiry after start, or an unconfirmed stop. It is never automatically replayed. Fake failure returns `failed`; a positively acknowledged Fake stop can return `timed_out`. Worker reserves the last 20% of the Profile time budget for stop acknowledgement and result transport; an unacknowledged stop becomes unknown at 90%. M2 must implement actual subprocess termination and stronger adapter lifecycle ownership.
- Completion is digest-idempotent for the same attempt/worker/token; changed completion returns 409. A stale attempt cannot start, heartbeat or complete. If result transport fails, the Worker propagates the error without rerunning the Agent; the caller may replay the **same completion**, or let its lease recover to unknown. There is no automatic execution retry endpoint in M1.
- Results retain task/attempt/worker/Profile/adapter attribution, status, times, summary, Markdown and private artifacts. M1 artifacts are bounded `text/plain` attachments: max five, <=1 MiB each, declared SHA-256 verified; JSON requests <=8 MiB. No arbitrary Worker filesystem paths or remote URLs are accepted. Markdown is stored as data; rendering/sanitization is M4.

## HTTP surface and authorization

`/v1` exposes multipart `POST /tasks`; paginated `GET /tasks?limit=1..100&cursor=<last-task-uuid>`; task detail and attachment reads; Worker `claim`, `start`, `heartbeat`, `complete` and `fail`. `fail` uses the same result envelope and refuses `succeeded`. Start/heartbeat/complete bodies use `{proof:{attemptId,token}, info? , result?}`. See the typed client/server for the exact M1 wire shape.

Every endpoint requires a Bearer device token from the operator registry. Registry entries bind token to `ownerId`, `deviceId` and role (`capture`, `viewer`, `worker`); request bodies cannot override identity. Capture creates/reads its owner's tasks, viewer only reads, Worker only claims and accesses the active assigned task's inputs plus fenced mutations. Tokens and completion digests are removed from history responses. File IDs are not bearer secrets. All responses disable caching; downloads force attachment/octet-stream plus `nosniff`. There is no public static blob route or request-body logging.

History currently scans the owner's small task collection in insertion order; pagination bounds responses, not database scan cost. Device revocation/rotation requires server configuration/restart. This is a personal M1 test registry, not an account management service. Cancel/review/retry UI and endpoint policies remain later milestones; the inherited logical protocol table describes the broader V1 surface.

## Remaining real-environment gates

No manual step is needed to establish M1's Fake/core HTTP gates. This work does **not** establish Windows tray/clipboard capture, real Codex login/image handling/sandbox/termination, public HTTPS, cross-device routing, notification delivery, installer behavior or production backup/restore. Their prerequisites, steps, expected observations and evidence boundaries remain individually specified in [Testing](TESTING.md) proofs A/B/C and [Roadmap](ROADMAP.md).

Recommended M2: implement the Worker-owned versioned Profile registry and Codex Adapter behind the existing `AgentAdapter`/`WorkerPort`, including bounded subprocess spawn (`shell:false`), input verification, timeouts/cancellation and uncertain-execution handling in both transports. Use fake child-process integration first; only the explicit real Codex smoke gate establishes authentication and actual sandbox behavior.
